# Context-sensitive routing

**Implementation design.** The chapter menu is source-derived; the selection algorithm and tie-breakers are this package’s adaptation.

## Evaluate the situation, not just its vocabulary

First identify the user’s requested outcome and the next unresolved bottleneck. Inspect observations, authority, stakes, urgency, relevant constraints, and previous attempts. Separate facts from interpretations. Do not infer that “unmotivated,” “difficult,” “resistant,” or “burned out” is a diagnosis.

Use a **qualitative fit check**, not an invented numeric score. The optional 0.2 runtime may supply real typed model values, explicitly labeled uncalibrated; they supplement rather than replace these checks: Does the desired outcome match? Do the actual observations support this kind of problem? Are the prerequisites present? Is the proposed action within the user’s authority and safe? What nearby explanation would change the route?

Choose one primary card. Add a second only when it removes a distinct barrier to the same outcome. A normal first response should not need more than two cards; this is a complexity budget, not a ban on a justified longer plan. Explain the useful sequence, complete the immediate task, and stop. Do not run a panel by default.

## Order when there are mixed signals

**Immediate harm or severe distress:** appropriate support and incident handling first. **Persistent impossible demands:** examine work and capacity, not just mindset. **Acute pressure blocking thought:** a brief reset can precede the main task. **Unknown situation:** understand before diagnosing. **No credible options:** generate before deciding. **Defined action involving people:** prepare or design the interaction. **Actual attempt completed:** reflect before generalizing.

A direct specialist request normally wins, unless its preconditions are missing or it would be unsafe. Explain the specific mismatch rather than silently substituting a different task. A user can request a source explanation without needing a real case.

## Important look-alike distinctions

| Presenting problem | Distinction that changes the route |
|---|---|
| “I don’t know what to do.” | Unknown causes → 1; understood problem but no options → 3; alternatives and trade-offs → 4. |
| “I have too much work.” | Personal commitments and leader contribution → 2; one unclear handoff → 11; team workload exceeds resources → 21. |
| “They aren’t performing.” | Specific behavior and impact → 12; capability and own thinking → 13; possible struggle and unknown context → 18; verified formal review/confirmed exit process → 20. Never jump straight to 20 from a label. |
| “They keep resisting.” | Goal or credible path missing → 8; behavior/incentive/friction mismatch → 9; disagreement about substance → 6; continuing relationship pattern → 17. |
| “I need a better meeting.” | The user’s stance → 5; understanding a leadership message → 10; team input and decision process → 7. |
| “The team isn’t working together.” | One shared goal → 8; continuing coordination and habits → 14; sustained capacity/working conditions → 21. |
| “Everyone is anxious.” | The user’s immediate steadiness → 15; honest continuity and action during upheaval → 16; a colleague needs support → 18; avoid diagnosing everyone. |
| “Something went wrong.” | Actual failure: stabilize/investigate/repair → 19; future choice under risk → 4; uncertain futures → 3 spotlight. |

For low-confidence cases, use the [material-action check](context-contract.md#clarification-must-change-the-next-move): state the ambiguity and ask one discriminating question only if its answer changes the next move; otherwise give grounded preparation or short conditional routes. Unknown cause need not block preparing an invitation, and close complementary fits need not require a user choice. A low library fit is not a reason to interrogate an adequately described ordinary task. Keep actual runtime outcomes intact and do not bypass human-review boundaries.

## Cross-cutting workflows

[Learn](workflows/learn.md) teaches one move; [rehearse](workflows/rehearse.md) practices a live interaction; [review](workflows/review.md) checks readiness and weaknesses; [panel](workflows/panel.md) uses the three book lenses; [debate](workflows/debate.md) examines a consequential unresolved trade-off; [compose](workflows/compose.md) handles a justified multi-part outcome; [reflect](workflows/reflect.md) learns from an actual attempt; [save](workflows/save.md) makes an approved lesson durable; [setup](workflows/setup.md) creates an optional learning home.

If no chapter fits, say so. The book is not a complete manual for legal, clinical, financial, technical, or every personal problem. Use a relevant part only within its scope, and clearly label any additional general reasoning or requested outside research.
